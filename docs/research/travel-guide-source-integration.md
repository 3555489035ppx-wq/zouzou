# 走走｜旅行攻略来源与合规接入研究

研究日期：2026-08-30

## 结论

可以参考小红书等平台的旅行攻略，但应把它们当作“用户体验线索”和“候选地点来源”，不能直接当作营业时间、价格、路程、库存或预约结果。真实行程仍必须用官方地点信息、地图路线和天气数据复核。

最适合走走的接入顺序是：

1. 用户主动粘贴公开攻略链接、上传攻略截图或复制文字；走走只解析用户提交的内容，并保留原链接。
2. 从攻略中抽取 `GuideCandidate`，例如地点名、玩法、适合时段、避坑提示和原文证据。
3. 用高德/其他有授权的 POI、路线和天气接口复核候选地点。
4. 在用户确认后才放入 `TripIntent` 和排程器；没有复核的内容只能显示为“攻略线索/待确认”。

不建议通过模拟登录、绕过验证码、批量抓取小红书页面或复制发布者的完整文字/图片来构建内容库。这种做法不稳定，也会带来平台规则、个人信息和著作权风险。

## 平台核查

### 小红书

- 小红书开放平台当前官方 API 参考页公开的接口目录主要是 OAuth 授权、Token、用户基本信息和解除授权等能力；页面没有把“按关键词搜索公开旅行笔记并批量读取全文”列为通用接口。见：[小红书开放平台 API 参考](https://openaccount.xiaohongshu.com/docs/api-reference)。
- 官方快速接入文档描述的是“用户点击、授权、返回应用、获取用户信息”的流程，不是攻略内容搜索接口。见：[小红书开放平台快速接入](https://openaccount.xiaohongshu.com/docs/quick-start)。
- 小红书官方社区公约要求借鉴或转载时核实来源，转载应取得对方同意并注明出处；官方侵权平台也明确保护文字、图片等权利。因此走走应优先保存链接和短摘要，不应复制整篇笔记或图片。见：[小红书社区公约](https://pgy.xiaohongshu.com/help/detail?id=1eda0a065dd894063c2e029a49e8f6a1&userType=4)、[小红书权利保护中心](https://ipp.xiaohongshu.com/)。
- 小红书分享开放平台更适合把走走生成的内容分享回小红书，而不是读取全站攻略。见：[小红书分享开放平台](https://agora.xiaohongshu.com/)。

结论：小红书可以作为“用户主动导入的攻略来源”，或者在取得官方合作/明确授权后接入；当前不应实现无授权的后台爬虫。

### B 站

- 本轮通过 OpenCLI 的公开搜索能力补充路线、美食和本地生活候选，只保存视频标题、作者、可用的发布时间/热度、来源链接和短线索，不复制视频、字幕或完整描述。
- 需要登录的字幕/总结接口不作为知识库依赖；因此 B 站内容只参与候选发现和排序，不能直接证明价格、营业时间、路线或预约状态。

结论：B 站公开搜索元数据可以作为低频社区候选源；若未来需要全文、字幕或后台持续同步，应先取得明确授权并单独评估平台规则。

### 携程及交易型平台

- 携程曾公开介绍旅游开放平台，覆盖内容导入/分销以及门票、玩乐、租车、接送机等交易接口，但这是供应商/分销商合作模式，不等于任何应用都可以读取携程社区攻略。见：[携程旅游开放平台公告](https://ttdopen.ctrip.com/apiplatform/help-detail.do?no=88)。
- 携程商旅也提供独立的开发者平台和接口调试流程，面向企业差旅合作场景。见：[携程商旅开发者平台](https://openapi.ctripbiz.com/)。

结论：携程适合作为获得授权后的酒店、门票、活动和订单事实源；攻略内容仍需按具体合作范围接入。

### 大众点评/本地生活平台

当前没有在本次核查中确认到可供走走直接使用的、公开且面向普通开发者的“全量攻略/评论搜索 API”。因此不应把网页抓取当作默认方案。若未来拿到正式合作接口，可把商家营业状态、地址、价格区间和用户评价摘要分别建模，并保留平台来源和更新时间。

## 推荐的数据结构

攻略线索不能直接复用 `MediaFact`，建议单独建立：

```ts
type GuideCandidate = {
  id: string
  platform: 'xiaohongshu' | 'bilibili' | 'user-import' | 'licensed-search'
  sourceUrl: string
  title: string
  author: string
  publishedAt: string | null
  fetchedAt: string
  summary: string
  tags: string[]
  placeHints: string[]
  foodHints?: string[]
  localExperienceHints?: string[]
  dietaryTags?: string[]
  claims: Array<{
    type: 'place' | 'activity' | 'tip' | 'route' | 'food'
    text: string
    placeName?: string
    confidence: number
    verified: boolean
  }>
  permission: 'user-provided' | 'licensed' | 'unknown'
}
```

排程器只允许 `verified: true` 的营业时间、路线、价格和预约信息成为硬事实；未验证内容可以用于推荐排序，但必须显示“来自攻略，出行前复核”。

## 对走走的实现建议

第一版先做“粘贴链接/上传攻略截图”而不是爬虫：

- 前端增加攻略链接输入和来源平台选择。
- 服务端只接受用户主动提交的 URL/截图，生成 `GuideCandidate`，限制长度、数量和缓存时间。
- LLM 只提取地点和体验描述，不提取为确定价格或营业状态。
- 通过 POI 服务做地点消歧，通过路线/天气服务做事实复核。
- 结果展示三种标签：`用户原话`、`攻略线索`、`已验证事实`。
- 用户点击“加入行程”后才进入排程，并保留来源链接和撤销操作。

这样既能吸收小红书里的真实体验，也不会让一篇可能过期或带推广性质的笔记直接改变用户的行程。

## 本轮执行记录（2026-08-30）

- 使用用户控制的 Google Chrome 会话确认小红书登录状态；未读取密码、验证码、Cookie 或浏览器本地存储。
- 通过低频只读采集补充 20 个城市的 B 站公开搜索结果；小红书保留已有来源并接入了少量已成功读取的笔记详情。上一轮采集完成时 `data/travel-guides.json` 共 390 条摘要，其中 B 站 282 条、小红书 108 条。
- 结构化字段新增 `foodHints` 与 `localExperienceHints`，用于把“本地小吃”和“本地人项目”送入候选时间轴；所有社区线索仍标记为待核验。
- 小红书后续批量搜索出现连续空结果，网页搜索交互也发生超时，因此没有继续高频重试或删除已有小红书数据。再次采集应使用更长间隔、分批执行，并保留失败时的旧数据。
- 按 B 站 → 小红书 → 公开百科/官方页面 → 百度检索的轮换方式做了小批量核查：B 站补查武汉过早、南京音乐台/欢乐谷、杭州早市/夜市；小红书同批查询因接口频控返回空结果；百科接口连接超时；百度公开结果补到了武汉“过早”和热干面的线索。
- 城市事实层从原先仅上海、长沙的精选条目扩展为 20 城、199 条结构化候选，覆盖知名景点、城市漫步、本地小吃和本地生活项目。南京新增“中山陵音乐台”和“南京欢乐谷”，武汉新增“黄鹤楼、东湖、湖北省博物馆、武汉欢乐谷、过早”等；这些候选保留地图 POI 来源，价格、营业和预约状态仍不作为静态事实。
- 用户意图新增结构化 `dietary`：`avoidSpicy`、`avoidSeafood`、`vegetarian`、`halal`、`allergies`、`dislikes`。本地解析器、远程 JSON Schema、社区检索、城市条目筛选和最终行程校验共用同一套饮食风险判断；未明确说出的限制不会被猜测。
- 官方核查记录：南京中山陵园管理局说明音乐台位于中山陵广场东南侧，并列出中山陵、明孝陵、灵谷、音乐台等景点；湖北省文化和旅游厅列出湖北省博物馆地址与职能；南京欢乐谷保留官方游玩页；杭州市文旅部门发布的精品线路包含西湖、灵隐寺和西溪湿地。对应链接：[音乐台](https://zschina.nanjing.gov.cn/fjms/jqjd/ylt/)、[中山陵景区景点](https://zschina.nanjing.gov.cn/fjms/)、[湖北省博物馆](https://wlt.hubei.gov.cn/zfxxgk/fdzdgknr/jgjj/zsdw/202008/t20200805_2740545.shtml)、[南京欢乐谷](https://nj.happyvalley.cn/play/index.shtml)、[杭州文化旅游精品线路](https://wgly.hangzhou.gov.cn/module/download/downfile.jsp?classid=0&filename=c3ccb4250d3143a09047ee20fbe1170c.pdf)。

## 第二、三轮扩充记录（2026-08-30）

- 将 20 城事实层扩充到 630 条命名候选，每城 30–34 条；其中 503 条为景点/活动，127 条为小吃或餐饮候选。每城都包含知名地标、特色景点、室内/雨天备选、城市漫步、本地小吃和至少一个本地生活节点。第二、三层扩充数据集中在 `src/services/trip/cityKnowledge.expanded.ts` 与 `src/services/trip/cityKnowledge.special.ts`，由 `cityKnowledge.ts` 统一导出给排程器。
- 采集器新增 `attraction` 主题（“必去景点 + 小众景点 + 攻略”），并改为按来源 ID 增量合并，后续补采不会清除已有城市攻略。第二轮 B 站景点专题按小批次覆盖 20 城，当前社区摘要为 464 条：B 站 356 条、小红书 108 条；小红书景点专题因接口频控返回空结果，旧数据保留，没有把空结果解释为“没有内容”。
- 这轮用 Trip.com 公开体验搜索做交叉观察：武汉结果出现湖北省博物馆讲解、东湖/沉浸式演出线索；南京结果出现中山陵—明孝陵—美龄宫—音乐台组合；杭州结果出现西湖演出、龙井采茶、灵隐寺与西湖组合；长沙、昆明、三亚结果分别出现橘子洲/岳麓书院、石林/滇池、南山/大小洞天等组合。只将其作为路线组合和体验类型的研究线索，不把商业套餐的价格、销量或评价写成静态事实。保留的公开链接示例：[武汉湖北省博物馆体验](https://us.trip.com/things-to-do/detail/97722587/)、[南京钟山组合](https://us.trip.com/things-to-do/detail/101734870/)、[杭州龙井采茶](https://us.trip.com/things-to-do/detail/102143519/)、[长沙橘子洲/岳麓书院组合](https://us.trip.com/things-to-do/detail/94243678/)、[昆明石林](https://us.trip.com/things-to-do/detail/81314740/)、[三亚南山/大小洞天](https://us.trip.com/things-to-do/detail/32555956/)。
- 成都、厦门、北京的官方页面进一步用于核对“景点应有预约/开放提示”的类型边界：熊猫基地公布实名预约和分时入园提示；厦门市政府把鼓浪屿、集美学村、胡里山炮台、五缘湾、沙坡尾等列入文化与滨海旅游资源；故宫官方购票页明确提示通过官方渠道预约。对应链接：[成都大熊猫繁育研究基地](https://m.panda.org.cn/cn/)、[厦门市人民政府旅游意见](https://www.xm.gov.cn/zwgk/flfg/sfwj/202109/t20210901_2580031.htm)、[故宫在线订票](https://www.dpm.org.cn/subject_booking/index.html)。
- 携程搜索联想可返回城市、地标和景区候选，但携程景点列表接口需要数字城市 ID，武汉本轮请求超时；大众点评搜索触发验证码。没有绕过验证码、模拟登录或把未验证商户写入知识库。正式接入这类平台时仍应使用授权 API 或用户主动导入。
- 现有 `GuideCandidate`、城市候选和排程器的匹配关系保持不变：用户输入城市/天数/偏好/忌口 → 先筛出明确饮食风险 → 按必去地点和偏好匹配 20 城候选 → 再加入社区发现的小吃/本地项目/景点线索 → 生成日程并保留来源链接；未验证条目不会成为营业、价格、预约或路线硬事实。
